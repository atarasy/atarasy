# iOS-first contract pack

Status: executable subset, not a complete or production-ready API. The accompanying source manifest pins read-only Git objects. All examples and presentation fixtures are synthetic. Dummy base64 assertions deliberately cannot establish cryptographic authority.

## Contents

- OpenAPI 3.1 inventory for selected existing routes, with external JSON Schema 2020-12 files.
- Eighteen existing client subset schemas: requests, publication payloads, query and response projections, including mandate read-back.
- One proposed private operation envelope, explicitly unimplemented and separate from strict public request bodies.
- Fifteen positive/negative request examples and five proposed-envelope validation cases.
- Two households, two merchants and four presentation-model offers. These are UI fixtures, not complete server seed commands or evidence of deployed isolation.
- Eleven canonical vectors generated from the Web reference and checked independently by Swift and pinned engine functions, including statements with a missing (`lost`) line and a disputed one (question 46).

## Interpretation

Schema-valid is not signature-valid, authorised or financially eligible. Empty settlement requests are structurally valid for some protocol paths and do not permit an unsigned consumed physical statement. Collection candidate membership and permitted verdict changes need server state. The native request subset deliberately excludes bare signatures, uses standard base64 and bounds integers to the JavaScript safe range. Those restrictions are client policy and must not be misreported as exact server rejection behavior.

Statement response data includes null carriage when delivery is absent. The native prototype rejects signing in that condition even if a response carries a challenge. A disputed line retains its original amount in canonical statement bytes with its disputed flag; do not zero the signed amount merely because the charge excludes it.

The initial Swift codec conservatively rejects delimiter-bearing decision/statement identifiers and duplicate UTF-8 candidate identifiers. This is a bounded prototype client policy, not a new protocol restriction. Canonically equivalent Unicode spellings remain distinct byte identities, and sorting follows JavaScript UTF-16 ordering.

## Incomplete contracts

Full publication signature coverage, exhaustive route-specific refusal coverage, identity/session protocol, permissions, recovery/export and the operational coordinator remain incomplete. Selected success projections and the generic error envelope are now executable. OpenAPI default response descriptions retain the unknown-outcome boundary. There is no production server URL or security scheme pretending that the reference authenticates callers.

The proposed envelope's digest and actor binding require service verification; regex/type validation proves neither. Source metadata and examples make the next contract work reproducible but do not close CP-B01 or protected-release gates as a whole.

## Measured response pack

`response-examples.json` contains 44 responses captured from the pinned reference HTTP handler in process, with source hashes and the harness hash. Unlike `fixtures.json`, these are actual serialised reference responses. The harness uses the engine's ephemeral test keys and bare signatures solely to reach protocol states; it proves no native authenticator, session, network or provider behavior. The temporary sources are read from Git objects and no listener is started. UUIDs, timestamps and test signatures change when recaptured, so validate each capture instead of requiring identical regenerated bytes.

Run `python3 scripts/ios-first/verify-engine-responses.py --engine-repo /path/to/valence --output /path/to/capture.json` with Bun on PATH. To intentionally replace the committed capture, update the Swift test resource copy with it. The schema validator exercises the 44 captured responses and 88 missing/extra-field cases. Creation and presentation responses support fixture setup. Selected publication request schemas and five positive/negative request cases are now included; semantic signature constraints remain server obligations.

The record verifies one-presenter query filtering, paid/gift goods totals, consumed disputes, unchanged original receipt on identical signed replay/read-back, a conflicting changed confirmation, and absence of the private delivery code from these projections. Query filtering and deployment-role refusal are not caller authentication. `not_found` on settlement lookup is not proof that an earlier mutation had no effect.

`SettlementResponse.charged` equals kept plus undisputed consumed goods. Carriage is signed in the statement but absent from this settlement projection; currency and provider payment status are also absent. A client must not label this amount a complete paid total or add a second goods effect. A real integration result needs the separate verified outcome/financial projection described in the integration requirements.

The Swift `ReferenceResponseReader` validates settlement resource identity using UTF-8 bytes, required/closed fields, safe integers, duplicate candidates, eligible line states/disputes and all amount breakdowns. Unknown refusal codes retain their status and code; raw server messages are not exposed. Unexpected HTTP/media/JSON outcomes remain failures. It is a decoder for received read responses, not a network adapter, write/retry facility or authorisation check. Other response schemas are currently validated in the contract pack, not yet modelled as Swift screen inputs.

## Publication and mandate increment

OpenAPI 0.3 adds configuration publication, disclosure publication, offer creation, configuration/acknowledgement results and mandate read-back. Configuration signatures are required by this client contract even though the HTTP parser accepts omission before signature verification refuses it. Safe-integer and nonempty-string checks remain client restrictions. Signatures in these merchant publication requests are not native household assertions.

The 44-response harness checks duplicate configuration refusal, unsigned configuration refusal, altered disclosure refusal, frozen original offer price/disclosures after new publication, new offers using the new revisions, rejection of a candidate price override, mandate version conflicts, null versus zero ceilings and loosening with the previous co-signer. The key material is still ephemeral test-only material.

**Closed signature gap:** until the catalogue signature moved to `valence.catalogue.2`, `canonicalConfig` did not include `physical` eligibility, and the reference accepted a publication whose `physical.ambient` had been altered under the original signature. At the pinned revision the harness signs an ambient-eligible configuration, alters `physical.ambient` to false, and the reference refuses it with `422 bad_signature` (case `config-eligibility-signed`). Recorded 2026-09-15 when the pin moved to valence `67df231`.

**Pin moved to valence `dfffe4f` on 2026-09-15** (questions 48 and 49). Offer, offer-list and approval candidates now carry `collected_as`, which the three response schemas require, and the 44 responses were recaptured. The member detail, review and transaction packs were not recaptured; the Swift readers accept `collected_as` where an engine sends it on every candidate and treat its absence as an engine from before the field.

Swift mandate reads now bind the expected mandate and household by UTF-8 identity, require nullable fields to be present, preserve null/zero and allow lapsed records to be displayed. A caller may require a known minimum version. None of these checks grants authority to change the mandate or proves session authentication.
